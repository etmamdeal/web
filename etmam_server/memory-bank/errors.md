### 25/05/2024 - خطأ current_user غير متاح في القوالب
**الخطأ**: ظهور خطأ 500 Internal Server Error عند محاولة فتح الصفحة الرئيسية
**الملفات المتأثرة**:
- `app.py`
- `index.html`
- `base.html`

**التحليل**:
- القوالب تستخدم `current_user.is_authenticated` و `current_user.is_admin`
- Flask-Login لا يمرر `current_user` تلقائياً إلى القوالب في بعض الحالات
- هذا يسبب خطأ عند محاولة الوصول إلى خصائص `current_user`

**الحل**:
- إضافة `current_user` إلى context processor:
  ```python
  return dict(script_status_color=script_status_color, current_user=current_user)
  ```
- الآن `current_user` متاح في جميع القوالب

**الحالة**: تم الإصلاح - يجب التأكد من توفر جميع المتغيرات المطلوبة في القوالب

## مشكلة وميض المودال في صفحة إدارة المستخدمين
**تاريخ الاكتشاف**: [التاريخ الحالي]

### المشكلة
- وميض (flicker) في النوافذ المنبثقة (modals) في صفحة إدارة المستخدمين
- يحدث عند التفاعل مع زر إظهار/إخفاء كلمة المرور
- المشكلة تتفاقم مع وجود عدة نوافذ منبثقة في نفس الصفحة

### السبب التقني
- استخدام متغير `event` العمومي في دالة `togglePassword` بدون تمريره صراحةً
- اعتماد الدالة على الحدث الأوتوماتيكي من المتصفح
- تكرار الحدث بشكل غير متوقع عند وجود عدة modals
- تداخل الأحداث يؤدي إلى إعادة رسم المودال بشكل متكرر

### الحل المطبق
1. تعديل دالة `togglePassword` لتكون أكثر أماناً:
   - استخدام `document.activeElement` للحصول على الزر الحالي
   - تجنب الاعتماد على `event` العمومي
   - تحسين آلية العثور على أيقونة العين

2. الكود المحدث:
```javascript
function togglePassword(inputId) {
    const input = document.getElementById(inputId);
    const button = document.activeElement;
    const icon = button.querySelector('i');

    if (input.type === 'password') {
        input.type = 'text';
        icon.classList.remove('fa-eye');
        icon.classList.add('fa-eye-slash');
    } else {
        input.type = 'password';
        icon.classList.remove('fa-eye-slash');
        icon.classList.add('fa-eye');
    }
}
```

### النتيجة
- تحسن أداء النوافذ المنبثقة
- إزالة مشكلة الوميض
- تحسين تجربة المستخدم عند التعامل مع حقول كلمات المرور

### الدروس المستفادة
1. تجنب استخدام المتغيرات العمومية في معالجة الأحداث
2. استخدام `document.activeElement` للحصول على العنصر النشط بشكل آمن
3. أهمية اختبار الواجهة مع وجود عناصر متعددة من نفس النوع
4. ضرورة مراعاة تأثير الأحداث المتكررة على أداء الواجهة

## [23/06/2025] مشكلة `OperationalError: no such column: properties.images` (تحقيق معمق)

### الوصف
بعد حل سلسلة من الأخطاء المتعلقة بتسجيل الدخول، ظهر خطأ `no such column: properties.images` عند دخول العميل إلى لوحة التحكم الخاصة به. هذا الخطأ استمر بالظهور بشكل متكرر رغم محاولات إصلاحه المتعددة، مما استدعى تحقيقًا جذريًا.

### تاريخ المشكلة وتسلسل المحاولات الفاشلة

1.  **المحاولة الأولى (Migration الأساسية):**
    - **التشخيص:** عدم تطابق بين `models.py` (الذي يحتوي على عمود `images`) وقاعدة البيانات الفعلية (التي لا تحتويه).
    - **الإجراء:** تم تنفيذ `flask db migrate` لإنشاء ملف تحديث.
    - **النتيجة:** نجح إنشاء الملف.

2.  **المحاولة الثانية (مشكلة SQLite - ALTER TABLE):**
    - **التشخيص:** عند تنفيذ `flask db upgrade`، ظهر خطأ `(sqlite3.OperationalError) near "ALTER": syntax error`. المشكلة كانت بسبب قيود SQLite التي لا تدعم تعديل الأعمدة بنفس طريقة قواعد البيانات الأخرى.
    - **الإجراء:** تم تعديل `migrations/env.py` لتفعيل `render_as_batch=True`، وهي الطريقة الموصى بها للتحايل على قيود SQLite.
    - **النتيجة:** تم تعديل الملف بنجاح.

3.  **المحاولة الثالثة (مشكلة تاريخ التحديثات - Table already exists):**
    - **التشخيص:** عند إعادة تنفيذ `upgrade`، ظهر خطأ `table properties already exists`. هذا كشف أن تاريخ التحديثات في Alembic غير متزامن مع الواقع، غالبًا لأن الجدول تم إنشاؤه يدويًا في البداية.
    - **الإجراء:** تم حذف ملف التحديث الخاطئ، ثم تنفيذ `flask db stamp head` لمحاولة مزامنة التاريخ.
    - **النتيجة:** لم تنجح المزامنة وظهر خطأ `Target database is not up to date`.

4.  **المحاولة الرابعة (كشف الحقيقة - وجود ملفي قاعدة بيانات):**
    - **التشخيص النهائي:** بعد استمرار المشكلة، تم البحث عن جميع ملفات `.db` في المشروع، واتضح وجود نسختين:
        - `etmam_server/database.db`
        - `etmam_server/instance/database.db`
    - **السبب الجذري الحقيقي:** كانت أوامر `flask db upgrade` تقوم بتحديث قاعدة البيانات الموجودة في المجلد الرئيسي، بينما كان التطبيق الفعلي يقرأ من قاعدة البيانات الموجودة في مجلد `instance`، والتي بقيت قديمة ولم تتأثر بالتحديثات.

### الإجراء التصحيحي النهائي
- سيتم فحص `config.py` لتحديد المسار الرسمي لقاعدة البيانات بشكل قاطع.
- سيتم توحيد جميع العمليات (التطبيق وأوامر flask) لتشير إلى ملف قاعدة البيانات الرسمي الوحيد.
- سيتم إعادة تنفيذ `flask db upgrade` للتأكد من أنه يستهدف قاعدة البيانات الصحيحة هذه المرة.
